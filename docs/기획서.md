## 1. 개요

### 1.1 배경
인사 업무 PI 및 E2E 재설계 교육에서 프로세스 나열·도식화를 포스트잇과 수기로 진행해 왔다. 이 방식은
- 작성 결과를 수정·보관·공유하기 어렵고,
- 교육생마다 표기 방식이 달라 비교·취합이 어렵고,
- 진단(문제 유형, 개선 방향) 결과가 도식과 분리되어 관리된다.

### 1.2 목적
웹 브라우저에서 **프로세스 계층 정의 → 활동(L5) 나열 → 순서도 자동 생성·편집 → AS-IS 진단 → TO-BE 설계**까지 한 번에 할 수 있는 경량 툴을 만든다.

### 1.3 교육 운영 시나리오
| 단계 | 시점 | 누가 | 무엇을 | 사용 릴리스 |
|---|---|---|---|---|
| ① 사전과제 배포 | 2026-09-20 | 강사 → 교육생 30명 | `pi-canvas.html` 메일 첨부. L1–L3 체계 내장 | **R1** |
| ② 사전과제 작성 | 배포 ~ 교육 전 | 교육생 (1인 1개) | L1–L3 중 자기 업무를 골라 **L4 1개를 정하고 L5 활동을 나열**. `.json` 파일로 저장해 제출 | R1 |
| ③ 사전 검토 | 교육 전 | 강사 | 제출 파일 30개 취합·검토 | R2 |
| ④ 교육 당일 | `[확인 필요 Q1]` | 교육생 | 자기 파일을 열어 순서도 생성 → 다듬기 → 진단 → (TO-BE) | R2 / R3 |

### 1.4 설계 원칙
| 원칙 | 의미 |
|---|---|
| **설치·서버 없음** | HTML 파일 하나. 더블클릭으로 Edge에서 실행하며 사내망/오프라인에서 동작 |
| **파일 호환 보장** | R1에서 저장한 파일은 R2·R3에서 그대로 열린다(파일 포맷 버전 관리) |
| **범용성** | 인사 전용이 아니라 모든 PI 워크숍에 쓸 수 있는 구조. 인사는 첫 번째 템플릿 |
| **쉬운 표기법** | BPMN 2.0 핵심 요소만 사용 |
| **목록이 먼저, 그림은 자동** | 표로 입력하면 순서도 초안이 생성되고 그 위에서 다듬는다 |

## 3. E2E 관점 설계 가이드 (툴에 반영할 방법론)

- **E2E의 시작과 끝은 고객(현업·직원·지원자) 관점에서 정의한다.**
  예: 경력 채용 = "현업의 채용 요청" → "입사자 첫 출근 및 업무 투입"
- **Swimlane을 기본으로 한다.** 활동의 **부서** 값이 곧 레인이 된다. 인사팀 외에 현업 팀장, 지원자, IT, 총무, 재무, 외부 기관 등이 드러나게 한다. 인사팀 레인만 가득 찬 것 자체가 진단 포인트다.
- **프로세스화되지 않은 업무도 적는다.** "담당자 판단", "케이스별 상이" 같은 활동도 행으로 남기고 진단에서 표준화 대상으로 태깅한다.
- L4 속성에 **E2E 시작 / 종료 / 고객**을 필수 입력으로 두어 범위를 의식하게 한다.

## 5. 기능 요구사항

### F1. 프로세스 계층 & 과제 정보 (R1)
- **L1–L3 체계는 강사가 지정한 템플릿이 툴에 내장**되어 있다(교육생은 수정 불가, 선택만).
  - 템플릿 원본 `[확인 필요 Q3 — 강사 L1–L3 목록 수령]`
- 교육생 작업 흐름
  1. 작성자 정보를 입력한다: 이름, 소속, 직무
  2. L1 → L2 → L3을 차례로 선택한다(드롭다운 또는 트리).
  3. **L4 프로세스명을 직접 입력한다.** (1인 1개. 한 파일 = L4 하나)
  4. L4 속성을 입력한다.

     | 항목 | 필수 | 예시 |
     |---|---|---|
     | E2E 시작 (트리거) | ✅ | 현업 팀장의 채용 요청 |
     | E2E 종료 (결과) | ✅ | 입사자 첫 출근 |
     | 고객 | ✅ | 현업 부서, 입사자 |
     | 프로세스 오너 | | 인사팀장 |
     | 발생 빈도 | | 월 8건 |
     | 설명 | | 자유 기술 |
- 코드는 자동 부여한다(예: `HR.01.02` + L4 순번).

### F2. L5 활동 목록 입력 (R1 핵심)
- 표 형태로 L5 활동을 순서대로 나열한다. **이 표의 칸이 곧 3단 Activity 박스의 상/중/하단**이 된다.

  | 칸 | 필수 | 입력 방식 | 박스 위치 | 예시 |
  |---|---|---|---|---|
  | 순번 | 자동 | 행 순서 | — | 3 |
  | 유형 | ✅ | 활동 / 판단(분기) | 모양 | 판단 |
  | 부서 | ✅ | 자동완성 (한 번 쓴 값 재사용) | 상단 (= Swimlane) | 인사팀 |
  | 담당자(역할) | | 텍스트 | 상단 | 채용담당 |
  | 활동명 | ✅ | 텍스트, **명사+동사** | 중간 | 채용 요청서 검토 |
  | 시스템/도구 | | 칩 다중 선택 + 자유 입력 | 하단 | HRIS, 메일 |
  | 다음 단계 | | 비우면 다음 순번으로 연결. 판단 행은 `조건→순번` | 연결선 | 승인→4, 반려→1 |
  | 비고 | | 텍스트 | (주석) | 월말에 몰림 |

- 도구 기본 칩: `시스템(이름 입력)` `메일` `엑셀` `전화` `메신저` `대면` `종이/출력` `결재`
- 편집 편의
  - 행 추가, 삭제, 위아래 이동(드래그), 행 복제
  - Enter를 누르면 다음 행으로 이동
  - **엑셀 범위를 복사해 붙여넣으면 여러 행이 한 번에 입력된다.** (기존 엑셀 정리본 재활용)
- 입력 검증 (저장은 막지 않고 경고만 표시)
  - 필수 칸 누락
  - 활동명이 명사+동사 형태가 아님(예: "검토" 한 단어, "~함" 문장형)
  - 판단 행에 조건이 없음
  - 존재하지 않는 순번을 참조함
- 권장 분량 안내: L5 활동 **8–20개** (너무 적으면 L4가 너무 작고, 너무 많으면 L4를 쪼갤 것)

### F3. 순서도 자동 생성 & 편집 캔버스
- **R1 (여유가 있을 때): 읽기 전용 미리보기.** 표 옆에 자동 생성된 순서도를 보여준다. 교육생이 목록을 제대로 썼는지 스스로 확인하는 용도다.
- **R2: 편집 가능한 캔버스**
- 자동 생성 규칙
  - 부서별로 Swimlane을 만든다(첫 등장 순서).
  - 순번대로 좌→우로 배치한다.
  - 시작/종료 이벤트를 자동으로 추가한다.
  - 판단 행은 XOR 분기로 만든다.
  - 레이아웃 엔진: ELK.js
- 표기법: BPMN 2.0 핵심 요소

  | 요소 | 모양 | 용도 |
  |---|---|---|
  | 시작 이벤트 | ○ 얇은 원 | 프로세스 시작 (트리거) |
  | 종료 이벤트 | ◉ 굵은 원 | 프로세스 종료 (결과) |
  | Activity | ▭ 둥근 사각형 (3단) | 업무 활동 |
  | 배타 분기 (XOR) | ◇ × | 조건에 따라 하나의 경로 (예: 승인/반려) |
  | 병렬 분기 (AND) | ◇ + | 동시에 여러 경로 진행 (캔버스에서만 추가) |
  | Swimlane | 가로 레인 | 수행 부서 |
  | 시퀀스 흐름 | → 실선 화살표 | 순서 (분기 시 조건 라벨) |
  | 주석 | ⌐ 텍스트 | 비고 |

- 편집 기능 (R2)
  - 팔레트에서 끌어다 놓기로 요소 추가
  - 이동, 연결, 삭제, 실행 취소/다시 실행
  - 확대/축소, 미니맵
  - 레인 관리(추가, 삭제, 순서 변경, 이름 변경)
  - [자동 정렬]
- **표와 캔버스는 같은 데이터를 보는 두 화면**이다. 캔버스에서 박스를 추가하면 표에도 행이 생긴다.

### F4. 3단 Activity 박스 (R1 미리보기 / R2 편집)
```
┌──────────────────────────┐
│ 인사팀 · 채용담당          │  ← [상단] 부서 · 담당자 (레인 색상 띠)
├──────────────────────────┤
│     채용 요청서 검토       │  ← [중간] 활동명 (명사+동사), 가장 크게
├──────────────────────────┤
│ [HRIS] [메일] [엑셀]       │  ← [하단] 시스템/도구 칩
└──────────────────────────┘
      🔴B  ⏱D   → R        ← (진단 모드) 문제 유형 배지 + 개선 방향
```

### F5. AS-IS 진단 (R2)
- 상단 **[진단]** 버튼을 누르면 진단 모드가 켜진다. 박스나 표의 행을 선택하면 우측에 진단 패널이 열린다.
- 입력 항목 (Activity별)

  | 구분 | 항목 | 입력 방식 |
  |---|---|---|
  | 문제 유형 | Bottleneck / Delay / Waste | 복수 선택 |
  | 개선 방향 | Eliminate / Replace / Assist / Restructure / Keep | 단일 선택 |
  | 코멘트 | 문제 원인 / 개선 아이디어 | 자유 텍스트 |
  | 정량 지표 | 처리시간, 대기시간 (분/시간/일) | 숫자 + 단위 (선택 입력) |
  | | 발생 빈도 (월 n회), 투입 인원 | 숫자 (선택 입력) |

- **용어 정의 툴팁은 교육 자료의 정의를 그대로 사용한다.** `[확인 필요 Q4 — 정의 원문 수령. 명칭 "ERASK / ERARK" 확인]`
- 시각화
  - 박스 테두리 색은 개선 방향을 나타낸다(E 빨강, R 파랑, A 보라, Rs 주황, K 회색).
  - 박스 우상단 배지는 문제 유형을 나타낸다(B, D, W).
  - 범례를 항상 표시한다.
- 진단 요약 (L4 단위)
  - 유형별 건수
  - 총 처리시간, 총 대기시간, **리드타임**
  - **프로세스 효율** = 처리 ÷ 리드타임
  - 월 투입 공수
  - 수작업 도구(메일·엑셀·종이) 비중

### F6. TO-BE 설계 & 비교 (R3, 당일 사용 시 R2)
- **[TO-BE 만들기]** 를 누르면 AS-IS를 복제한다.
  - Eliminate 박스는 점선·흐리게 표시한다.
  - Replace, Assist, Restructure 박스에는 "변경 예정" 표식을 붙인다.
- [비교] 탭
  - AS-IS와 TO-BE를 나란히 표시한다.
  - 활동 수, 리드타임, 효율, 월 공수, 수작업 도구 수의 개선율(%)을 보여준다.

### F7. 저장 / 불러오기 / 내보내기
| 기능 | 릴리스 | 설명 |
|---|---|---|
| 자동 임시저장 | R1 | 브라우저 저장소에 수시로 저장. 다시 열면 "이어서 작성하시겠습니까?" |
| 파일 저장/열기 (`.json`) | R1 | **제출용 원본.** 파일명: `L4명_이름.json` |
| 이미지 내보내기 (PNG) | R2 | 순서도 + 범례 |
| 엑셀 내보내기 | R2 | 과제 정보, L5 목록, 진단, (R3) AS-IS/TO-BE 비교 |

### F8. 강사 취합 화면 (R2)
- 제출 파일 30개를 한 번에 끌어다 놓아 불러온다.
- 제출 현황 표: 이름, 소속, L1–L4, 활동 수, 레인(부서) 수, 필수 누락 경고 수
- L1–L3별 분포: 어떤 업무에 과제가 몰렸는지
- 행을 클릭하면 해당 과제를 읽기 전용으로 연다.
- 전체를 엑셀 한 파일로 내보낸다(교육생별 시트 또는 통합 시트).

### F9. 텍스트 가져오기 — 업무 설명서(줄글) → L5 목록 (R3)
- 툴에서 LLM API를 직접 호출하지 않는다(키 노출, 사내망 차단 문제).
- **프롬프트 복사 방식**
  1. 툴이 출력 형식이 지정된 프롬프트 템플릿을 제공한다.
  2. 사용자가 회사에서 허용된 LLM에 템플릿과 업무 설명서를 넣는다.
  3. LLM 결과(표/JSON)를 붙여넣으면 F2의 붙여넣기 파서로 L5 목록이 생성된다.
- 사내 LLM 존재 여부와 외부 LLM 사용 정책 확인 필요 `[확인 필요 Q5]`
- 사내 LLM API 직접 연동은 보안 협의 후 별도 검토

### F10. 도움말 & 예시 (R1)
- 첫 실행 시 3단계 안내: ① L4 정하기 → ② L5 나열 → ③ 저장해서 제출

## 7. 데이터 구조 (파일 포맷 v1 — R1에서 고정)

```jsonc
{
  "format": "pi-canvas", "version": 1,
  "meta": { "author": "홍길동", "dept": "인사팀", "job": "채용",
            "createdAt": "...", "updatedAt": "...", "appVersion": "R1" },
  "taxonomy": {                     // 코드와 이름을 함께 저장 → 체계가 바뀌어도 파일만으로 식별 가능
    "templateId": "hr-temp-2026-09",
    "l1": { "code": "HR", "name": "인사" },
    "l2": { "code": "HR.02", "name": "채용" },
    "l3": { "code": "HR.02.02", "name": "경력 채용" }   // 직접 입력한 항목은 code = ""
  },
  "process": {                      // L4 (1 파일 = 1 L4)
    "name": "채용 요청·승인", "startEvent": "...", "endEvent": "...",
    "customer": "...", "owner": "...", "frequency": "...", "description": "...",
    "activities": [                 // L5 — R1 입력 범위
      { "id": "a1", "kind": "task", "dept": "현업", "performer": "팀장",
        "name": "채용 요청서 작성", "tools": ["메일", "엑셀"],
        "next": [], "note": "" },
      { "id": "a3", "kind": "decision", "dept": "인사팀", "performer": "인사팀장",
        "name": "채용 승인 여부 판단", "tools": ["결재"],
        "next": [ { "to": "a4", "label": "승인" }, { "to": "a1", "label": "반려" } ] }
    ],
    "asis": null,                   // R2: { layout(pos, lanes 순서), 추가 노드/엣지, diag }
    "tobe": null                    // R3
  }
}
```
- **R2·R3 필드는 비워 두고 R1 필드 구조는 바꾸지 않는다.** 이 규칙으로 R1 제출 파일을 이후 버전에서 그대로 연다.
- `next`가 비면 다음 순번으로 연결한다. `next[].to` 는 활동 **id**(순번 아님)이므로 행 순서를 바꿔도 연결이 유지된다. 종료는 `"END"`.
- 진단(`diag`)은 R2에서 활동별로 추가한다.

## 10. 리스크 및 대응

| 리스크 | 영향 | 대응 |
|---|---|---|
| R1 개발 기간 2일 | 기능 누락, 버그 | R1은 **표 입력 + 저장**에 집중. 미리보기는 여유가 있을 때만. 배포 전 Edge 실사용 테스트 필수 |
| L1–L3 템플릿 수령 지연 | R1 배포 지연 | 템플릿을 **별도 설정 블록**으로 분리해 마지막에 교체. 늦으면 L1–L3 자유 입력으로 대체 배포 |
| 교육생이 L4 범위를 너무 크게/작게 잡음 | 당일 순서도 품질 저하 | 권장 L5 개수(8–20) 안내, 예시 파일, E2E 시작/종료 필수 입력 |
| 파일 분실 / 저장 안 하고 닫음 | 작업 손실 | 자동 임시저장 + 이어쓰기, 저장 안 한 변경이 있으면 닫을 때 경고 |
| 30명 파일명 규칙 미준수 | 취합 혼란 | 저장 시 파일명 자동 생성, 취합 화면은 파일명이 아니라 내부 메타데이터로 식별 |
| R1 → R2 호환 깨짐 | 사전과제 재작성 | 파일 포맷 v1을 R1에서 고정, R2에서 R1 샘플 파일 호환 테스트 |
| 교육 후 사용 안 함 | 투자 대비 효용 낮음 | 범용 구조(인사 = 템플릿), 유지비가 거의 없는 구조 |
